# Day 15 — AWS deploy (Terraform)

Infrastructure-as-code that stands up the whole Day 15 stack so you can deploy
it once and spend the lecture *explaining* the services rather than clicking
through the console. Everything is chosen to sit in the **AWS Free Tier**, and
`terraform destroy` shuts it all off in one command.

## What it builds

```
                          Internet
                             │
        ┌────────────────────┼───────────────────────┐
        ▼                    ▼                         ▼
   S3 website          EC2 t3.micro               Lambda (Function URL)
   (React frontend)    public subnet              hello-world
                       ├─ Express API :3100
                       ├─ Redis (local, on-box)
                       └─ CloudWatch agent
                             │ 5432 (SG → SG)
                             ▼
                       RDS Postgres (db.t3.micro)
                       private subnets, not public

   IAM roles on EC2 + Lambda · CloudWatch logs/alarm/dashboard · custom VPC
```

Maps 1:1 to the Notes: **EC2, Lambda, S3, RDS, CloudWatch, IAM, VPC/security
groups**. DynamoDB and Secrets Manager are intentionally left out (see below).

## Prerequisites (on your machine, not here)

1. **Terraform** ≥ 1.5 — `brew install terraform`
2. **AWS CLI** ≥ 2 — already installed here; configure credentials once:
   ```
   aws configure          # or: aws sso login
   aws sts get-caller-identity   # should print your account
   ```
   The IAM user/role you use needs permission to create VPC, EC2, RDS, S3,
   Lambda, IAM roles, and CloudWatch resources (AdministratorAccess is simplest
   for a personal lecture account).

## Deploy

From this `infra/` folder:

```bash
make init              # one-time: downloads the AWS provider
make deploy            # apply infra, build the frontend vs the live API, apply again
```

`make deploy` runs in two phases: it applies the infra first (so the EC2 API
URL exists), builds `monolithic-frontend` with that URL baked in via
`VITE_API_URL`, then applies again to upload the built site to S3. The first
apply takes ~5–10 minutes (RDS is the slow part). When it finishes:

```bash
make output
```

gives you the four URLs to demo:

| Output | What it is |
| --- | --- |
| `frontend_url` | React site served from S3 |
| `api_url` + `api_health_check` | Express API on EC2 (`/health` proves RDS is wired up) |
| `lambda_url` | Open in a browser → JSON from Lambda |
| `cloudwatch_dashboard_url` | EC2/RDS/Lambda metrics in one view |

The EC2 box needs an extra 2–3 minutes after apply to finish its bootstrap
(install Node/Redis, pull code, migrate, build, start). If `/health` isn't up
yet, give it a minute.

## Tear it all down

```bash
make destroy        # terraform destroy — removes every resource, stops all cost
```

RDS has backups off, `skip_final_snapshot`, and no deletion protection; the S3
buckets are `force_destroy`. So destroy never gets stuck asking for a snapshot
name or refusing to delete a non-empty bucket.

> Want to pause instead of delete? You can `aws ec2 stop-instances` and
> `aws rds stop-db-instance` to stop compute charges, but stopped RDS still
> bills for storage and auto-starts after 7 days. For a lecture, full
> `destroy` is cleaner and cheaper.

## Cost notes

| Service | Config | Free-Tier status |
| --- | --- | --- |
| EC2 | t3.micro, 10 GB gp3 | 750 hrs/mo for 12 months |
| RDS | db.t3.micro, 20 GB, Single-AZ, no backups | 750 hrs/mo for 12 months |
| S3 | 2 small buckets | 5 GB free |
| Lambda | 128 MB, Function URL | 1M requests/mo always free |
| CloudWatch | logs (7-day retention), 1 alarm, 1 dashboard | within always-free limits |
| VPC | subnets, IGW, security groups, **no NAT** | free |

The only classic surprise charge — a **NAT Gateway (~$32/mo)** — is
deliberately avoided by putting EC2 in a public subnet. Keep an eye on the
12-month clock and your region being `us-east-1`.

## Things left out on purpose

- **DynamoDB** — the app is pure SQL for now.
- **Secrets Manager** (paid) — the DB password is generated by Terraform and
  written into the EC2 `.env` by user-data. That's the exact anti-pattern the
  Notes describe; a great "here's what Secrets Manager fixes" moment.
- **The DB seed** — the app's seed is 10M+ rows. Bootstrap runs
  `drizzle-kit push` (schema only). The API works; tables are just empty.
- **HTTPS / CloudFront / a load balancer** — all upgrades beyond a cheap demo.

## How the app gets onto EC2

Terraform tars the backend source (minus `node_modules`), uploads it to a
private deploy bucket, and the instance pulls it on boot via its IAM role.
Change any backend source file and re-run `terraform apply`: the tarball's hash
changes, which replaces the instance so it redeploys the new code. No SSH, no
git credentials on the server.

## Troubleshooting

- **`/health` never comes up** — connect and read the boot log:
  ```bash
  aws ssm start-session --target $(terraform output -raw ec2_instance_id)
  sudo tail -n 100 /var/log/user-data.log
  sudo systemctl status monolithic
  sudo journalctl -u monolithic
  ```
- **Frontend bucket is empty** — you applied before building. Run
  `make frontend-build && terraform apply`, or build manually with
  `VITE_API_URL=$(terraform output -raw api_url)` and
  `aws s3 sync ../../monolithic-frontend/dist s3://<frontend-bucket>`.
- **`no valid credential sources`** — run `aws configure` / `aws sso login`.
```
